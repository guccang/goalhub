# 员工用量与交付追问修复

2026-09-28 根据本机计算器目标记录排查。

## 原因

- 计算器目标包含 19 次模型调用：规划 1、分配 7、执行 8、最终验收 3；另有 12 次本地验收命令。
- 去重并按会话累计基线差分后的统计为 4,005,364 tokens，其中缓存输入 3,660,160。累计用量包含多次工具调用反复读取上下文，不等于提示词或上下文窗口大小。
- 交付快照将最近失败记录中的配置作为顶层 config 返回，模型误认成优先于仓库文件的人工覆盖。实际上 settings.delivery 为空。由此产生三次索要交付面板信息的问题，最后员工访问管理 API 又被运行锁拒绝。
- 每轮重复发送原始事件、完整已完成任务、员工说明及历史构建日志，长期复用会话使重复读取进一步累积。普通重试也会清空分配，多花一次负责人调用。

## 修复

- 当前人工配置与历史 release.config 分离，configSource 明确为 saved 或 repository；传给员工的交付信息只包含真实人工覆盖和标记为历史的构建证据。
- 构建验证端口被占用时自动选择空闲端口并记录实际地址，不修改用户配置或终止占用进程。用户手动指定的预览端口仍严格执行，冲突明确报错。
- 上下文保留当前目标、待办、问答、补充要求与必要测试证据，移除重复原始事件和冗余字段。一个历史样例从 26,095 字符缩减至 4,538 字符（约 83%）；这不是未来 token 费用的保证。
- 同一宿主会话累计 4 轮或上报上下文达到 48,000 tokens 后换新会话，从持久化项目状态继续；短会话仍复用，记录不删除。
- 第一次普通执行或测试重试沿用原员工，重复失败或评估改派仍交负责人。保留最终测试和独立验收。
- 提示词明确平台与员工的职责、当前目标优先于旧岗位中的旧目标，以及必要问题的原因、所需信息和推荐选择；问答面板同时显示阻断摘要。

## 验证

新增回归覆盖配置来源、真实端口冲突、上下文去重、会话轮换和首次重试。保留原有必要凭据问答、人工计划确认、失败修复、跨目标历史及用量差分测试。没有为验证节省效果再调用付费模型。
