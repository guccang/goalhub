# 项目交付

完成流程：任务与自动测试通过 → 最终审查 → 构建交付 → 验证安装包或 Web 启动 → 合并源码 → 发布交付入口。

新目标会要求开发员工在仓库根目录维护 `goalhub.delivery.json`。交付不通过时创建修复任务；缺少 SDK、签名或外部凭据时员工应请求用户输入。不会因源码和测试完成就忽略交付。

## Web

```json
{
  "kind": "web",
  "build": "npm run build:delivery",
  "verify": "npm run test:delivery",
  "preview": "npm run preview -- --host 127.0.0.1 --port {port} --strictPort",
  "port": 4173,
  "instructions": "点击启动预览，服务就绪后打开预览。"
}
```

示例命令需要项目真实提供相应脚本。`build:delivery` 必须负责安装依赖和构建；使用当前宿主系统支持的语法。失败步骤须返回非零退出码。Windows 命令通过 Windows PowerShell 执行，不应直接依赖 Bash 语法。

系统从已提交源码创建独立持久化仓库，在其中运行构建命令。首次交付先启动服务并验证根路径 HTTP 200–399，再停止验证用进程。源码合并后，用户可指定 1024–65535 的端口启动预览，看到“运行中”后打开独立浏览器页面，也可停止预览。端口被占用时显示错误，不终止无关程序，不自动切换端口。预览命令必须显式绑定 `127.0.0.1` 并使用 `{port}`。

服务默认最多等待 30 秒就绪；构建和验证命令各最多运行 30 分钟。预览进程退出后状态转为失败；关闭 GoalHub 会停止其持有的进程。异常退出后旧进程可能仍占用端口，需要在系统中确认处理，页面不会把未知进程显示为可用。

## 桌面与 App

```json
{
  "kind": "android",
  "build": "node scripts/build-delivery.mjs",
  "verify": "node scripts/verify-package.mjs",
  "artifacts": ["build/app/outputs/flutter-apk/app-release.apk"],
  "instructions": "目标 Android 版本、APK 的安装方法及权限说明。"
}
```

- `desktop`：支持 `.exe`、`.msi`、`.msix`、`.dmg`、`.pkg`、`.zip`、`.deb`、`.rpm`、`.AppImage`。便携 ZIP 必须包含可运行程序和必要资源。
- `android`：提供可直接安装的 APK。
- `ios`：提供已签名 IPA，说明设备与分发条件；需要实际具备对应构建、签名环境。
- 安装交付必须有 `build`、`verify`、`artifacts` 和 `instructions`。验证脚本应检查真实安装或启动条件，不能使用始终成功的占位命令。
- 文件必须在交付源码目录内且非空，系统校验常见格式文件头，再保存大小和 SHA-256。安装可用性仍依赖项目真实的验证脚本和目标平台环境，不能把文件头检查当作设备安装测试。
- 下载只接受交付编号与文件序号，校验受管路径和完整性，不公开任意文件路径。

## 源码项目与旧项目

仅库、脚本、文档等无需界面的项目可使用 `{"kind":"source","instructions":"无需安装包的理由和使用方法"}`。最终审查需确认类型与需求匹配。

项目标题下的“项目交付”面板可查看进度和日志。“交付设置”保存的是项目级覆盖配置，优先于仓库文件；“使用仓库配置”可取消覆盖。配置在开发与构建期间禁止修改。已完成的旧目标可先配置，再点击“构建交付”，不需要重新开发源码。

产物与预览依赖保存在 `data/deliveries/<交付编号>/`，不随开发 worktree 清理。交付记录绑定目标和提交号，历史目标保留自己的产物；重新构建使用新的目录，失败不会改写此前已保存的安装包。未合并的交付不会开放下载或手动预览。
