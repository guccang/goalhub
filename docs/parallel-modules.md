# 模块并行与实际接口集成

项目可配置模块并行或逐项执行、任务拆分粒度以及最多同时执行的任务数。新登记项目默认模块并行；没有此配置的旧目标继续使用串行流程。项目策略作为后续目标默认值，每个新目标可以单独覆盖。修改项目默认策略须先暂停项目，不会改变历史或正在执行目标。

## 规划与交接

主管提前定义模块大致职责、负责范围及数据输入输出，不要求预先锁定字段、函数签名、请求路径或数据库结构。员工在自己的任务工作区根据实现决定具体接口，并在结果的 `handoff` 中交付实际接口位置、示例、验证方式和限制。

任务阶段分为 `implementation`、`integration`、`verification`。多个模块需要明确的、有开发权限的集成任务，依赖相关模块成果；集成员工实际修改调用、转换数据和处理错误，不能只执行测试。模块使用模拟数据的自测不能替代真实业务链路验收。

大目标可通过 `modules` 保存模块概要，近期模块标记 `expanded` 并列出具体任务，远期模块标记 `deferred`。当前批次完成后，主管继续细化剩余模块并保留已完成任务及验收编号。存在未细化模块时，不进入最终交付。

## 执行与版本

每个任务版本有独立的 `goalhub/task-<id>-v<version>` 分支和工作区。无前置依赖的任务可以同时执行；同一员工在模块开发、自测和集成期间持有租约，不会被另一个目标重入。项目任务槽位限制实际并行任务数，单个目标也受自己的并行上限约束。

任务按 `pending → running → self_testing → queued_merge → integrating → done` 推进；另有 `paused`、`blocked`、`cancelled` 状态。任务失败最多自动尝试三轮，其他独立任务仍可推进。依赖只有在前置任务 `done` 后才满足，取消不等于完成。

重规划采用稳定任务编号和递增版本。未变更任务保留状态；修改说明、完成条件、数据交互、依赖或验收条件时产生新版本。旧运行结果必须通过任务版本检查才能接纳。会话按任务、版本和工作目录隔离，不能借用其他模块会话。

员工个人计划按运行记录持久保存；自动验收阶段继续显示同一员工、同一任务版本的最近计划。自测和集成测试分别记录代码提交、任务版本、命令和结果，不将其他工作区的自测当作当前集成结论。

## 集成与交付

通过模块自测的任务按完成顺序进入目标内串行集成队列。每项成果从最新已验证的目标分支建立临时候选，合并后回归当前模块与此前已接纳模块。冲突由员工在候选目录修复。失败不会更新目标分支；失败候选可保存回任务分支，下一轮根据实际集成问题修复。

只有准确的候选提交通过验证并且任务版本仍有效时，才快进目标分支。候选提交先登记到数据库，服务重启后可以通过 Git 祖先关系识别已经发生但尚未写完状态的合并。

全部必要任务通过且模块已经细化完毕后，复用目标级全量验收、最终评估、构建与交付流程。跨目标合并继续使用项目仓库锁。主分支更新后清理已接纳且干净的任务 worktree；失败、取消和未解决冲突的工作区保留，以免丢失成果。

## 用户介入

模块并行目标的自由输入先保存到 `control_requests`，同一目标按到达顺序处理。系统安全暂停该目标后，主管返回 `resume`、`pause`、`replan`、`cancel_tasks` 或 `pause_tasks` 决策。明确的停止或暂停指令不等待模型判断，也不会自动恢复。

页面提供暂停、取消、恢复单项任务的入口。当前控制方式先停止目标内进程并保存各任务检查点，再修改指定任务状态，按原运行情况恢复其他可执行任务。取消已经接纳的代码需要主管另建修订或清理任务，不能通过删除记录撤销代码。

输入队列、任务记录和工作区均持久化。服务重启时未知进程状态保持暂停，未应用的指令标记为中断，用户可查看并重新发送。模型调用失败时目标保持暂停，错误不会导致默认继续。

## 验证

`test/parallel-modules.test.mjs` 使用真实 Git 仓库、隔离目录和可控宿主验证同目标并行、接口适配、取消依赖、自然语言暂停、连续输入、任务版本、冲突修复和失败集成隔离。既有串行与跨目标调度测试继续保留。
