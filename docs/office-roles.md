# 项目、员工与宿主

项目定义目标、架构、仓库和规范；员工属于项目，通过职位定义工作内容；全局宿主配置提供认证与执行能力。项目只需指定一名负责人，不要求固定四类职责，也不按职责轮换员工。

## 项目团队

办公室的「管理员工」打开项目团队：左侧展示像素人物、姓名和职位，右侧编辑职位名称、工作说明、宿主、模型、思考强度、语言和时限。人物选择同步姓名，办公室和列表使用相同人物资源。

每个项目最多 15 人。可以保存空团队或未完成的职位草稿；开始执行时，必须有一名启用的负责人，且所有启用员工都填写职位名称与工作说明。负责人可以亲自承担任务，单员工项目也可以运行。

「项目上下文与语言」保存架构、需求背景和长期规范。每轮输入组合项目上下文、员工职位定义、当前任务及相关历史。具体需求继续通过项目迭代管理。

复制其他项目的团队时生成新的员工编号，仅复制配置，不复制会话或工作记录。保存前只是当前窗口草稿；复制后双方独立修改。关闭窗口不保存。

## 负责人和任务

负责人通过规划轮次拆解需求，并为每项任务填写本项目启用员工的真实编号 `assignee`。服务端校验员工和任务依赖。任务按依赖串行执行，各员工使用自己的宿主、模型与职位说明。

负责人定期读取独立源码快照与运行证据，提出继续、修复或必要提问。失败任务、最终验收新增任务、已移除或停用员工的未完成任务，由负责人重新分配。分配原因记录为 `task.assigned`。同一负责人正在执行任务时不并发启动自己的评估。

所有任务完成后，系统运行全部验收命令，由负责人核对交付证据，通过后合并项目主分支并移除开发 worktree。`planner`、`coordinator`、`developer`、`evaluator`、`final-review` 是内部运行阶段，不是必须配置的员工职位。需要独立审查时，负责人应将审查列为明确任务并指派合适员工。

## 持久化和兼容

团队保存在 `settings.employees`，共享上下文保存在 `settings.context`。员工包含 `id`、`character`、`name`、`position`、`instructions`、`isLead`、`enabled` 和宿主执行参数。旧的 `role` 仅作为迁移历史记录的线索。

旧项目首次加载时将固定职责转换为职位说明，以原规划员工为负责人，保留员工编号、历史任务和执行快照。历史轮次不改写；当前姓名按人物统一。默认员工在项目创建时固定，后续目标或宿主默认配置不会重建团队。

API 为 `GET/POST /api/projects/:id/employees`，提交内容包括 `employees`、可选 `context` 与 `language`。服务端拒绝运行中修改。删除或停用员工只清除其未完成任务的指派，历史执行记录继续保留。

每次实际调用的员工身份、职位、模型等保存到 `runs.executor`。会话按项目、员工、执行阶段和配置指纹隔离；更改职位说明、项目上下文或宿主参数会开启新会话，并继续携带项目历史摘要。页面按员工展示持续工作会话。

## 宿主和模型

员工页面与全局宿主设置复用动态模型选择器：打开、切换宿主或点击刷新时查询目录。Codex 使用实际执行的认证环境查询 `model/list`；其他宿主尚无统一枚举适配时明确显示说明，允许输入自定义模型。目录可见不等于实际调用已通过测试。

思考强度目前仅 Codex 可配置，具体选项仍需所选模型支持。

## 办公室与设施

负责人使用办公室主座位；普通员工使用项目工位。人物状态来自员工编号关联的真实轮次，任务看板使用任务实际执行者，交接消息来自持久化事件。

测试工作站是独立设施，只对应真实测试进程，不生成额外员工。散步、喝咖啡等环境动画不表示 Agent 在执行任务。
