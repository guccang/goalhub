# 项目上下文

每次员工调用和提示词预览使用同一份五部分上下文。原始目标不再以“唯一产品目标”置顶，用户后续决定可以修订它。

| 部分 | 内容 | 边界 |
| --- | --- | --- |
| 项目资料 | 仓库、平台、团队、交付配置 | 自由文本背景仅供负责人核对，不能覆盖当前需求 |
| 当前需求 | 有效摘要、必做、延期、排除、来源编号、来源版本 | 由负责人结合原始目标与用户决定整理；程序不猜测授权范围 |
| 本轮任务 | 当前任务、必要依赖、验收命令、待处理修复 | 执行和分配阶段不注入其他无关任务；修复不改变产品范围 |
| 当前状态与证据 | 最新轮次、当前阻断、关联验收时间和命令版本 | 旧结果标明历史或上次尝试；宿主启动失败不能被旧验收失败覆盖 |
| 历史记录索引 | 原始诉求、决策来源编号、已处理修复、构建版本 | 原始记录仍在项目详情、执行记录及 Git 中查询，默认不反复注入正文 |

## 当前需求如何产生

原始目标、已回答问题和需求补充构成来源清单，问答和补充按同一时间线排列。单纯“继续当前目标”不算新增需求；明确选择“修复执行问题”的意见也不进入需求来源。

负责人规划必须返回 `requirements`，包括 `summary`、`included`、`deferred`、`excluded`、`sourceRevision` 和 `sourceIds`。平台核对来源版本和全部来源编号，再与任务、验收项一起原子保存。延期、排除的语义是否符合用户授权仍需负责人和最终审查判断，字段校验不代表语义自动正确。

用户决定或项目背景变化后，旧快照不再标记有效。旧项目尚无快照时显示 `needs-consolidation`，暂时提供明确标记的原始来源；下一次负责人规划必须完成整理。不会直接篡改历史目标或自动宣布原有任务完成。

执行阶段只接收有效需求，不重复接收已被整理的原始问答和旧背景。负责人重新规划时仍可核对全部来源，避免丢失用户授权。

## 修复与恢复

阻断表单默认“修复执行问题，保留当前需求”；改变产品范围需要选择“修改需求，重新规划”。普通继续操作恢复原阶段，不能自动解决程序路径、登录或环境故障。

待处理修复单独传递，员工用 `resolvedRepairIds` 明确说明实际处理的意见，关联任务验收通过后才归档。重规划会解除旧任务编号绑定，未处理意见继续保留，不会随着旧计划消失。旧错误输出按时间与当前阻断区分；源码变化后上一轮验收仍可作为修复线索，但不作为当前源码已通过或失败的结论。

## 会话与历史

规划、分配和执行会话仅在同一目标、同一需求来源版本及同一员工配置下复用。需求变化或切换目标后使用新会话，旧运行记录保留。旧版未记录需求版本的会话不再续接。

`requirement_snapshots` 保存当前需求；`requirements.consolidated` 事件保留历次整理；`instructions.kind` 区分需求、修复和继续操作，`resolved_at` 标记已处理修复；`runs.requirement_revision` 记录每轮使用的需求来源版本。
